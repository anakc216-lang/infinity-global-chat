# Automatic message cleanup and chat host

Run [chat-host-and-room-cap-migration.sql](./chat-host-and-room-cap-migration.sql) once in the Supabase SQL Editor. It enforces a rolling maximum of 3,500 rows per room: when a new message would exceed the cap, the oldest row in that room is permanently deleted, leaving the newest 3,500. It also removes the prior global 200,000-message purge trigger so that it cannot erase all rooms before their individual cap is reached, records room activity, and adds the private RPCs used by the scheduled host.

The Render configuration also runs `node server.js --chat-host-cycle` every minute. There is no four-minute quiet period: each run registers the configured country rooms, checks up to 200 rooms with no newer activity, and posts at most one clearly marked host message per eligible room. Delivery is checked on the once-per-minute cron schedule, so it is not instantaneous within the same second. Posts are sent in batches of 20 with a short pause between batches; the database rechecks room activity before each insert. Host names and conversation starters rotate from a small built-in set; this does not use an AI provider and does not provide live news or real-time topic summaries. The cron service requires `SUPABASE_SERVICE_ROLE_KEY`.

The 3,500-per-room cap does not depend on the separate 24-hour retention migration. If enabled, [chat-message-24-hour-retention-migration.sql](./chat-message-24-hour-retention-migration.sql) additionally removes messages older than 24 hours every five minutes and requires `pg_cron`. Clients load only a small recent window (up to 50 rows initially and at most 80 in local memory), remove evicted rows on Realtime delete events, reconcile with the current database snapshot on room reload/reconnect, and render new messages as they arrive; they do not fetch or display all 3,500 retained messages at once.

Both room-limit trimming and retention permanently delete rows from the live table. Keep a Supabase backup/PITR plan if messages may need recovery. The app keeps only a small local chat window; it removes stale cached rows when it reconciles with Supabase and naturally drops older local rows as new messages arrive.

The 3,500 limit applies to rows in `public.messages`; it is not a byte-based Supabase storage quota. Image objects use Supabase Storage and need their own cleanup policy. The repository's separate sticker cleanup job removes chat-sticker objects older than 24 hours.
